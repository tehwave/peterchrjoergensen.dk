I was testing a Quickpay payment flow in a local WordPress and WooCommerce project. The payment worked, then Quickpay had no route to the callback on my laptop. It cannot send a request to my `localhost`.

A tunnel gives Quickpay a public URL that forwards requests to my machine. WordPress cares about its URL, so the tunnel brings extra work. A temporary hostname can affect redirects and cookies. It can also change generated links and HTTPS behaviour. I wanted to test the payment integration without reconfiguring the site around a tunnel.

Quickpay already had the payment state I needed. My local application already knew how to receive a callback and verify its signature. The CLI could fetch the payment, build the expected body, sign its bytes, and send it straight to the local callback route.

I could have put that code into the WordPress project. Then I would have to build it again for the next shop. A standalone CLI could sit beside any project.

It also gave coding agents a small interface to work with. They can inspect `--help` and run a command without learning the PHP structure of the host application. JSON output gives them a stable result. A developer can use the same tool from a terminal. That is how [Quickpay CLI](https://github.com/tehwave/quickpay-cli) began.

I chose Laravel Zero because I knew Laravel's conventions and wanted to spend my time on the commands. The project targets PHP 8.4 and Quickpay API v10. Composer installs a PHAR, so the tool does not become part of the application it is helping me test.

The first version handled payments. It could create and inspect them, make payment links, show operations, capture funds, refund a payment, or cancel it. A guarded raw command covered API calls that had no dedicated command.

Human-readable output goes to the terminal. `--json` gives scripts and agents a stable result. Commands that change a payment ask for confirmation unless the caller passes `--yes`. The API key can come from `QUICKPAY_API_KEY` or a protected local file.

The payment commands worked. The local callback problem remained.

I added `callbacks:replay` and an early version of `callbacks:watch`. The first watcher required a payment ID. That made sense in code and felt clumsy at the terminal. When I test a shop, I want to start the watcher before I create the payment.

The command now watches for new operations across the account. A payment ID or order ID can narrow the search when I need it.

```bash
quickpay callbacks:watch \
  --to=http://127.0.0.1:8000/quickpay/callback
```

The watcher records the time when it becomes ready, then asks Quickpay for payments changed after that point. Each polling window overlaps the previous one by a second. A payment ID paired with an operation ID prevents duplicate delivery across that overlap.

When a payment changes, the CLI fetches its current state and finds operations it has not seen during the session. It creates one request for each new operation. The exact JSON bytes are signed with HMAC-SHA256 and sent to the URL from `--to`.

Quickpay callbacks use the `Quickpay-Checksum-Sha256` header. My local code therefore runs its usual signature check instead of accepting a convenient unsigned request. Quickpay describes the checksum in its [callback documentation](https://learn.quickpay.net/tech-talk/api/callback).

The callback client is separate from the API client. Quickpay credentials stay with requests to `https://api.quickpay.net`, and the callback destination receives none of the API headers. The private key stays in memory while the request is signed.

Polling returns the latest payment state from Quickpay. The callback body is not a copy of the historical request sent when the operation first happened. If two operations appear between polls, both requests may contain the same payment snapshot.

For local testing, I accept that difference. The application gets a correctly shaped request with a valid signature, while the rest of the WordPress site remains on my machine.

Payment commands need stricter rules than a normal read-only API tool. Quickpay's base URL and API version live in one client. Commands supply relative paths. Pagination accepts HTTPS links back to the Quickpay API and rejects foreign hosts. It also rejects unusual ports, fragments, cycles, user information, or too many pages.

Polling can retry a failed read. Payment mutations stop after a network failure because the result may be uncertain. If a capture reached Quickpay and only the response was lost, an automatic retry could repeat the action.

Capture and refund commands ask for confirmation. Cancellation and non-GET raw requests do the same. Stored credentials use atomic writes with private directory and file permissions. An environment variable takes priority, which keeps a key out of the local config in CI.

JSON stays on stdout. Prompts and diagnostics go to stderr. This lets a script parse the result without a status line appearing inside the JSON document.

The retry policy for callbacks changed after a blunt manual test. I pointed the watcher at a route that returned HTTP 405. The original version kept retrying forever to preserve callback order. My terminal filled with requests that could never succeed.

The watcher now retries network failures, 408, 425, 429, and server errors. It makes five attempts in total by default. Other failed HTTP responses stop immediately. The command exits with an error and suggests `callbacks:replay` once the route has been fixed.

The first release verified the wrong artifact. Our workflow produced a checked PHAR and attached it to GitHub. I then followed the README and installed the package through Composer. Composer pulled Laravel Zero and its dependency graph instead of the standalone executable I expected.

The workflow had checked the GitHub asset. Packagist installs the files in the tagged repository archive.

The repository now contains the versioned `builds/quickpay` PHAR and exposes it as the Composer binary. Laravel Zero stays in `require-dev` and is bundled inside the PHAR. A distribution test checks that package shape, and the release instructions include a clean Composer installation.

ChatGPT and Codex wrote most of the implementation. They researched the APIs, drafted plans, wrote code, and ran reviews. I chose the product scope and the command interface. I set the safety requirements and tested the awkward paths. I rejected answers that solved a smaller problem than the one I had described.

During an architecture review, I mentioned the test folders while explaining that the repository felt disorganised. The first answer reorganised the tests. I had to send it back and ask for the whole repository. The next pass grouped production code and tests around the same capabilities.

The README took several passes too. Some versions made callbacks sound like the entire product. Others read like sales copy. I kept cutting until the text matched the tool I was using.

For a shorter introduction to the tool, read [Quickpay CLI brings payment callbacks to localhost](/blog/quickpay-cli-payment-callbacks-localhost/).

`callbacks:watch` remains a local development tool. It watches payment operations, while subscription callbacks are outside its scope. The process runs in the foreground and keeps its cursor in memory. Operations that already exist when the watcher becomes ready are ignored. Ordering is preserved for each payment, while operations from different payments have no global order.

The automated callback tests use HTTP fakes. They prove the CLI's behaviour against the fake transport. The live Quickpay contract remains outside the test. I keep those limits in the documentation because they change how the command should be used.

Quickpay CLI installs globally through Composer:

```bash
composer global require tehwave/quickpay-cli
```

After `quickpay login`, the commands cover the full payment flow as well as callback replay and watching. The [public repository](https://github.com/tehwave/quickpay-cli) has the command reference and current limitations.

I now have one tool I can run beside WordPress or Laravel projects. It gives me the payment data I need and delivers a signed request to my local callback route. That solves the papercut I started with.
